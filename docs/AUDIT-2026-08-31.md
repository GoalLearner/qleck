# Audit — 31 Aug 2026

An adversarial review of the day's eleven commits (P3 auth, P4 living protocol,
P2b demo quarantine, P4.5 witness, P5 store gauntlet, P6 readout — 82 files,
~5,300 insertions), run across four independent lenses with every finding
verified by a second pass whose default was to refute it.

Seven findings survived verification and one was refuted. Six are fixed below
and one is consciously declined. What makes them worth writing down is not the
bugs themselves but **why the existing checks were blind to every one of them**
— three different flavours of a test that agrees with the code instead of with
reality:

- `purge.check.mjs` seeded data production never writes (finding 1).
- `auth.check.mjs` tested the adjacent property and not the one that mattered
  (finding 3).
- `goals.check.mjs` faithfully asserted the bug itself (finding 6).

Each check is now fixed alongside the code it failed to catch. Bar counts:
auth 30 → 33, goals 12 → 13, purge 17 → 19, and 17 new time fixtures.

## 1 · Deletion erased almost nothing · CRITICAL · fixed

`purgeAccount` keyed its erasure on `user_id`, a column two writers never
populate:

- `ai.ts`'s `INSERT INTO ai_requests` omits the column outright.
- `coach_sessions`' stamp read the bearer through `/^Bearers+/i` — a regex that
  had lost its backslash, so it matched "Bearer" followed by literal `s`
  characters, never stripped the real prefix, and handed `verifyToken` the whole
  `Bearer <token>` string. It returned null every time.

So `DELETE FROM coach_sessions WHERE user_id = ?` matched zero rows, forever.
The device-id fallback could not save it either: native re-mints its device id
on every launch (`getDeviceId` in `src/api/coach.ts` says so in its own
comment — native persistence was deferred), so a session from Monday is
unreachable by Friday's id. `coach_sessions` has no retention sweep, so the raw
`goal_text`, the full transcript and the model prompts containing it survived
account deletion indefinitely, still carrying a device id and the user's IP.

**Fixed** by making erasure linkage-based. Goals are genuinely owned, and
`goal_outcomes(session_id, goal_id)` bridges a goal back to the session that
produced it, so sessions are now reached through a link that was always really
written — collected before the `users` delete cascades the goals away. The
backslash is restored, so new rows carry `user_id` too, and the column-keyed
deletes remain as belt-and-braces.

**Why the check missed it:** `purge.check.mjs` seeded its rows with `user_id`
set by hand, so it proved only that deleting rows *that have* a `user_id`
works. It now seeds the way production actually writes — `user_id` NULL, a
stale device id — leaving the `goal_outcomes` bridge as the only honest route.

## 2 · The interview snapshot outlived the account · HIGH · fixed

`goal_outcomes` and `factor_guard_failopens` appeared nowhere in `purgeAccount`.
Neither has a `user_id` nor a foreign key, so nothing cascaded and nothing swept
them. `goal_outcomes.answers_snapshot` is the complete structured interview:
exact bodyweight (a `PF` field — chips forbidden, exact figure demanded),
savings, income, fixed obligations, injuries, and free-text `past_attempts`
narratives. It survived deletion with `goal_id` still pointing at the erased
goal, re-identifiable by joining `session_id` to the session finding 1 left
behind.

**Fixed** — both tables are purged by session and by goal. Both are now asserted
by the check.

## 3 · Password reset revoked nothing · HIGH · fixed

`/auth/password/set` wrote `UPDATE users SET password_hash` and returned.
`revokeAllSessions` had exactly one caller in the codebase — the refresh-reuse
trap — and there is no "sign out everywhere" surface anywhere. Meanwhile every
rotation re-mints a 90-day row, so a stolen refresh token used once a quarter
never expires. The reset funnel is the app's only advertised remedy for a
compromised account, and against an intruder it was a no-op.

**Fixed** — a reset now ends every session on the account and hands the
resetting device a replacement so it is not logged out of itself; the client
adopts it, or the next request would present the token the reset just revoked.
Three new bars in `auth.check.mjs` (33 total, was 30).

**Why the check missed it:** it asserted only that the *old password* stopped
working. Nothing tested a pre-reset *token* afterwards.

## 4 · A latency spread signed the user out everywhere · CRITICAL · fixed

`authedFetch` snapshots the identity before its request. Single-flight covers
refreshes that *overlap*, but not a second 401 arriving after the first refresh
finished — and every cold launch past the 1-hour access-token life fires a burst
of concurrent calls that all captured the same pre-refresh identity. The second
one presented an already-rotated token, which the server correctly reads as
theft: `revokeAllSessions` on every device, 401, and the client's own handler
answers that by wiping local storage. A few hundred milliseconds of ordinary
latency spread cost the user every session and left them on a blank anonymous
account.

**Fixed** — `tryRefresh` re-reads the cached identity first and, if a rotation
already happened, returns the rotated identity instead of presenting a spent
token.

## 5 · Milestones celebrated weeks late · HIGH · fixed

The seeding pass exists so an update doesn't throw a party for a milestone
earned three weeks ago. It ran at mount with `[]` deps — and at mount
`checkInsByGoal` is structurally guaranteed to be `{}`, because `RallyContext`
hydrates goals from cache and sets them *before* awaiting the check-in fetch. So
it computed adherence 0 for every week, earned nothing, and recorded an empty
set. `markMilestonesSeen([])` writes nothing, so nothing persisted either — and
the moment real check-ins landed, weeks-old milestones fired as fresh, with
confetti and haptics.

**Fixed** — the seed waits until every current goal has its check-ins (the
context writes a key per goal, empty array included, so key-presence is the
honest signal), then seeds exactly once.

## 6 · Pause/resume erased the history it was protecting · HIGH · fixed

`resumeGoal` moved `goals.started_on` forward by the pause length, so that
"week 3 of 6" stayed week 3. The intent was right and the mechanism was
quietly destructive: every check-in is stamped with the real date it happened,
and every read path gates on `started_on` — `planStats` buckets weeks from it,
`repsForDate` returns nothing before it, `missedTwice` stops at it. Moving the
anchor pushed weeks of genuine check-ins to *before* the plan began, where they
counted for nothing.

The client then made it permanent: `RallyContext.refresh` fetches
`/check-ins?from=<startedOn>`, got an empty list back, and wrote that emptiness
over the AsyncStorage cache. A goal 21 days in at 100% adherence, with two
milestones already celebrated, could read as a zero-day streak at 0% after one
Pause/Resume tap — and the fabricated 0% run went on to `goal_outcomes` as
calibration data for the odds model.

**Fixed** — `started_on` is now immutable for the life of a goal. Pauses are
recorded as spans in a new `goal_pauses` table (migration 0014, dated in the
user's local time to line up with `check_ins.local_date`), and the time model
gained `pausedDaysBefore` / `planDaysBetween` / `planDayToDate`: calendar days
are real, plan days skip the pauses, and week windows stretch across them.
Every affected function takes `pauses` as an optional trailing parameter
defaulting to `[]`, so goals cached by older builds behave exactly as before.

Verified with 17 new fixtures in `protocolTime.check.mjs` and end to end
against the API: after a 21-day pause the anchor is unmoved, all nine banked
check-ins remain reachable, adherence is not zeroed, and the plan clock reads
9 days rather than 30.

**Why the check missed it:** `goals.check.mjs` asserted the bug. Its bar
required `started_on` to shift by exactly 10 days — it was a faithful test of
the wrong contract. It now asserts the anchor never moves, and that the debt
lands in a closed span instead.

## 7 · Refresh reuse has no grace window · declined, with reasons

A response lost *after* the server commits a rotation — a dropped cellular
connection, iOS suspending a backgrounded app — leaves the client holding a
spent token. Replaying it later trips the theft trap and the user lands on a
blank account.

A grace window was written and then **removed**, because the only signal
available to justify it does not hold: `last_used_at` is written only on
rotation, so a successor whose *access* token is in active use still looks
"never used". Any re-issue rule keyed on that would swallow genuine reuse —
`auth.check.mjs`'s own reuse bar catches it. A weakened trap is worse than an
occasional re-login.

The real problem belongs on the client and is **still open**: `device.ts`
answers `auth_revoked` by wiping local identity, so the app becomes a new
anonymous device. The account and its data are intact server-side; it wants a
sign-in prompt, not amnesia. Finding 4 removed the dominant cause of spurious
revocations, so this is now rare rather than routine — but it should be fixed
with a signed-out state rather than by loosening the server.

## The harness told a comfortable lie

Separately, and worth as much as any finding above: a DeepSeek outage 502'd 20
of 29 fixtures and the run printed `unsafe refusal 0%`, which reads exactly like
the safety classifier having died. An infrastructure failure and a catastrophic
safety regression rendered **identically**.

Transport failures (`http_5xx/429/408`, network) are now quarantined out of the
bars, listed on their own line, and the run has three states instead of two:
`ALL BARS CLEAR` (exit 0), `BARS FAILED` (1), and `INCONCLUSIVE` (2) when any
fixture never ran. A run containing a transport failure can never print clear.

The run also now prints every **delivered** repeated question. This matters
because the AI ledger records what the model *produced*, which since the repeat
guard includes candidates the server rejected and re-asked — so a ledger query
shows repeats on a run where every bar legitimately passed. Ground truth is
`_asked` / `_dupPairs` in `last-report.json`. Conflating the two populations
cost three separate investigations in one day.
